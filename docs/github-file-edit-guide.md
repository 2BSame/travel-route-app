

# GitHub 파일 수정 및 제출 가이드

이 문서는 팀 프로젝트에서 GitHub를 처음 사용하는 팀원들이 파일을 수정하고 제출하는 방법을 설명하기 위한 문서입니다.

우리 프로젝트에서는 각 팀원이 자신이 맡은 파일을 수정한 뒤, 바로 최종본에 반영하지 않고 **Pull Request**를 통해 수정 내용을 제출합니다.

---

## 1. GitHub 작업의 기본 흐름

GitHub에서 파일을 수정하는 기본 흐름은 다음과 같습니다.

```txt
자신이 맡은 파일 찾기
↓
파일 열기
↓
오른쪽 위 연필 버튼으로 수정하기
↓
Commit changes 작성하기
↓
새 branch 생성하기
↓
Pull Request 생성하기
↓
팀장 또는 담당자가 확인하기
↓
문제 없으면 main에 Merge하기
```

쉽게 말해, GitHub에서는 파일을 수정한 뒤 바로 최종본에 넣는 것이 아니라, 먼저 “제가 이렇게 수정했습니다. 확인해주세요.”라는 요청을 올립니다.  
이 요청이 바로 **Pull Request**입니다.

---

## 2. 역할별로 수정해야 하는 위치

모든 팀원이 GitHub에서 파일을 수정하는 방식은 같습니다.  
다만 역할에 따라 수정해야 하는 폴더와 파일이 다릅니다.

---

### 2.1 데이터 담당자

데이터 담당자는 주로 `data/` 폴더를 수정합니다.

```txt
data/
├─ places.json
├─ busStops.json
└─ busSchedules.json
```

| 작업 내용 | 수정 파일 |
|---|---|
| 장소 데이터 추가 및 수정 | `data/places.json` |
| 버스정류장 데이터 추가 및 수정 | `data/busStops.json` |
| 버스 시간표 추가 및 수정 | `data/busSchedules.json` |

데이터 파일을 수정할 때는 반드시 데이터 입력 가이드북에 적힌 양식을 지켜야 합니다.

---

### 2.2 UI 담당자

UI 담당자는 주로 화면과 컴포넌트 관련 파일을 수정합니다.

```txt
src/components/
src/screens/
app/
```

| 작업 내용 | 수정 위치 |
|---|---|
| 버튼, 카드, 공통 UI 수정 | `src/components/` |
| 화면 구성 수정 | `src/screens/` |
| 앱 시작 화면 수정 | `app/` |

---

### 2.3 알고리즘 담당자

알고리즘 담당자는 주로 `src/algorithms/` 폴더를 수정합니다.

```txt
src/algorithms/
```

| 작업 내용 | 수정 위치 |
|---|---|
| 장소 필터링 | `src/algorithms/filterPlaces.ts` |
| 루트 생성 | `src/algorithms/routeMaker.ts` |
| 추천 점수 계산 | `src/algorithms/scoreCalculator.ts` |

파일 이름은 프로젝트 구조에 따라 달라질 수 있으므로, 실제 저장소 구조를 확인한 뒤 작업합니다.

---

### 2.4 문서 담당자

문서 담당자는 주로 `README.md`와 `docs/` 폴더를 수정합니다.

```txt
README.md
docs/
```

| 작업 내용 | 수정 위치 |
|---|---|
| 프로젝트 전체 설명 | `README.md` |
| 데이터 작성 규칙 | `docs/data-guide.md` |
| 회의 내용 정리 | `docs/meeting-notes.md` |
| 기능 설명 문서 | `docs/` 내부 문서 |

---

## 3. GitHub 웹사이트에서 파일 수정하는 방법

처음 GitHub를 사용하는 팀원은 VS Code나 Git 명령어를 사용하지 않아도 됩니다.  
GitHub 웹사이트에서 직접 파일을 수정할 수 있습니다.

---

### 3.1 GitHub 저장소에 접속하기

팀장이 공유한 GitHub 저장소 링크로 들어갑니다.

예시:

```txt
https://github.com/팀장아이디/프로젝트이름
```

저장소에 들어가면 다음과 같은 파일과 폴더가 보일 수 있습니다.

```txt
README.md
docs/
data/
src/
app/
package.json
```

---

### 3.2 자신이 맡은 폴더로 들어가기

자신의 역할에 맞는 폴더로 들어갑니다.

예를 들어 데이터 담당자가 장소 데이터를 수정한다면 다음 순서로 이동합니다.

```txt
GitHub 저장소 접속
↓
data 폴더 클릭
↓
places.json 클릭
```

---

### 3.3 파일 오른쪽 위의 연필 버튼 누르기

파일을 열면 오른쪽 위에 연필 모양 버튼이 있습니다.

```txt
Edit this file
```

또는 화면에 따라 연필 아이콘만 보일 수도 있습니다.

```txt
✏️
```

이 버튼을 누르면 GitHub 웹사이트에서 파일 내용을 직접 수정할 수 있습니다.

---

### 3.4 파일 내용 수정하기

연필 버튼을 누르면 파일을 편집할 수 있는 화면이 나옵니다.

이때 다음 규칙을 지켜야 합니다.

```txt
1. 자신이 맡은 부분만 수정합니다.
2. 다른 팀원이 작성한 내용을 임의로 지우지 않습니다.
3. 기존 파일 구조를 최대한 유지합니다.
4. 데이터 파일의 경우 입력 양식을 반드시 지킵니다.
5. JSON 파일의 경우 괄호와 쉼표가 깨지지 않도록 주의합니다.
```

특히 `.json` 파일은 형식이 깨지면 앱에서 데이터를 불러오지 못할 수 있습니다.

---

## 4. Commit changes 작성하기

파일 수정을 끝냈다면 화면 아래쪽으로 내려갑니다.  
아래쪽에 **Commit changes** 영역이 있습니다.

여기에는 자신이 무엇을 수정했는지 간단히 적습니다.

---

### 4.1 좋은 Commit 메시지 예시

```txt
월영교 장소 데이터 추가
```

```txt
210번 버스 시간표 수정
```

```txt
메인 화면 버튼 디자인 수정
```

```txt
추천 점수 계산 방식 수정
```

```txt
데이터 입력 가이드 문서 수정
```

---

### 4.2 좋지 않은 Commit 메시지 예시

```txt
수정
```

```txt
ㅇㅇ
```

```txt
작업함
```

```txt
테스트
```

Commit 메시지는 나중에 누가 어떤 작업을 했는지 확인하는 기록이 됩니다.  
따라서 가능한 한 구체적으로 작성하는 것이 좋습니다.

---

## 5. main에 바로 저장하지 않기

파일을 수정한 뒤 저장할 때 다음과 같은 선택지가 나올 수 있습니다.

```txt
Commit directly to the main branch
```

```txt
Create a new branch for this commit and start a pull request
```

우리 프로젝트에서는 가능하면 아래 선택지를 사용합니다.

```txt
Create a new branch for this commit and start a pull request
```

이 선택지는 수정한 내용을 바로 최종본에 넣지 않고, 검토용 수정본으로 제출한다는 뜻입니다.

반대로 아래 선택지는 가능하면 사용하지 않습니다.

```txt
Commit directly to the main branch
```

이 선택지는 수정한 내용을 바로 최종 파일에 반영하는 방식입니다.  
초보자가 실수로 main에 바로 저장하면 앱 실행 오류가 생기거나 다른 팀원의 작업과 충돌할 수 있습니다.

---

## 6. Pull Request 생성하기

새 branch를 선택해서 저장하면 Pull Request를 만들 수 있는 화면이 나옵니다.

Pull Request는 쉽게 말해 다음과 같은 의미입니다.

```txt
제가 이 파일을 이렇게 수정했습니다.
확인해보고 괜찮으면 최종본에 반영해주세요.
```

---

### 6.1 Pull Request 제목 예시

```txt
월영교 장소 데이터 추가
```

```txt
안동구시장 버스정류장 데이터 추가
```

```txt
메인 화면 UI 버튼 수정
```

```txt
추천 점수 계산 함수 수정
```

```txt
GitHub 작업 가이드 문서 추가
```

---

### 6.2 Pull Request 설명 예시

```txt
월영교 장소 데이터를 추가했습니다.
테마는 산책, 사진, 야경으로 설정했고 예상 체류 시간은 60분으로 입력했습니다.
```

또는 다음처럼 적어도 됩니다.

```txt
변경 내용:
- places.json에 월영교 데이터 추가
- 가까운 버스정류장 id 연결
- 테마와 태그 입력

확인 요청:
- JSON 형식이 맞는지 확인 부탁드립니다.
- 장소 테마가 적절한지 확인 부탁드립니다.
```

---

## 7. 팀장 또는 담당자가 확인한 뒤 Merge하기

Pull Request를 만들었다고 해서 바로 최종본에 반영되는 것은 아닙니다.

팀장 또는 해당 파트 담당자가 Pull Request를 확인합니다.

확인할 내용은 다음과 같습니다.

```txt
1. 수정한 파일이 맞는가?
2. 입력 형식이 깨지지 않았는가?
3. 다른 팀원의 작업을 지우지 않았는가?
4. 앱 실행에 문제가 없는가?
5. 가이드북 규칙을 지켰는가?
```

문제가 없으면 팀장 또는 담당자가 **Merge**를 눌러 `main`에 반영합니다.

Merge가 완료되면 해당 수정 내용이 프로젝트의 공식 파일에 포함됩니다.

---

## 8. 전체 작업 예시

### 예시: 데이터 담당자가 월영교 데이터를 추가하는 경우

```txt
1. GitHub 저장소에 접속한다.
2. data 폴더에 들어간다.
3. places.json 파일을 클릭한다.
4. 오른쪽 위 연필 버튼을 누른다.
5. 데이터 입력 가이드북의 양식에 맞춰 월영교 데이터를 추가한다.
6. 화면 아래 Commit changes 영역으로 내려간다.
7. Commit 제목에 “월영교 장소 데이터 추가”라고 적는다.
8. main에 직접 저장하지 않고 새 branch 생성을 선택한다.
9. Pull Request를 만든다.
10. 팀장에게 “월영교 데이터 PR 올렸습니다”라고 알린다.
11. 팀장이 확인 후 문제가 없으면 Merge한다.
```

---

### 예시: UI 담당자가 버튼 디자인을 수정하는 경우

```txt
1. GitHub 저장소에 접속한다.
2. src/components 폴더에 들어간다.
3. 수정할 UI 컴포넌트 파일을 클릭한다.
4. 오른쪽 위 연필 버튼을 누른다.
5. 버튼 디자인 코드를 수정한다.
6. Commit 제목에 “메인 화면 버튼 디자인 수정”이라고 적는다.
7. 새 branch를 만들고 Pull Request를 생성한다.
8. 팀장 또는 UI 담당자가 확인한 뒤 Merge한다.
```

---

### 예시: 문서 담당자가 가이드북을 수정하는 경우

```txt
1. GitHub 저장소에 접속한다.
2. docs 폴더에 들어간다.
3. 수정할 문서 파일을 클릭한다.
4. 오른쪽 위 연필 버튼을 누른다.
5. 문서 내용을 수정한다.
6. Commit 제목에 “데이터 입력 가이드 문서 수정”이라고 적는다.
7. 새 branch를 만들고 Pull Request를 생성한다.
8. 팀장 또는 문서 담당자가 확인한 뒤 Merge한다.
```

## 9. 팀원 공통 규칙

우리 프로젝트에서는 모든 팀원이 다음 규칙을 지켜야 합니다.

```txt
1. main에 직접 commit하지 않습니다.
2. 자신이 맡은 파일만 수정합니다.
3. 수정 전 가이드북을 먼저 확인합니다.
4. Commit 메시지는 알아보기 쉽게 작성합니다.
5. 수정 내용은 Pull Request로 제출합니다.
6. 한 번에 너무 많은 내용을 수정하지 않습니다.
7. 오류가 생기면 혼자 해결하려 하지 말고 팀장 또는 담당자에게 알립니다.
8. 다른 팀원의 작업 내용을 임의로 삭제하지 않습니다.
9. 파일 구조를 잘 모를 때는 먼저 질문합니다.
```

## 10. Pull Request를 올린 뒤 팀원에게 알리는 방법

Pull Request를 만들었다면 팀장 또는 담당자에게 간단히 알려주세요.

예시:

```txt
월영교 장소 데이터 PR 올렸습니다.
확인 부탁드립니다.
```

```txt
메인 화면 버튼 디자인 수정 PR 올렸습니다.
문제 있으면 말해주세요.
```

```txt
210번 버스 시간표 데이터 수정했습니다.
Pull Request 확인 부탁드립니다.
```

## 11. 자주 생기는 실수

### 11.1 main에 바로 저장하는 경우

가능하면 하지 않습니다.  
수정 내용은 Pull Request로 제출합니다.

---

### 11.2 JSON 파일에서 쉼표를 빠뜨리는 경우

데이터 파일에서 쉼표가 빠지면 앱이 데이터를 읽지 못할 수 있습니다.

예를 들어 여러 항목 사이에는 쉼표가 필요합니다.

```json
[
  {
    "name": "월영교"
  },
  {
    "name": "안동찜닭골목"
  }
]
```

---

### 11.3 다른 팀원의 내용을 지우는 경우

자신이 맡은 부분만 수정합니다.  
잘 모르는 코드는 삭제하지 않습니다.

---

### 11.4 Commit 메시지를 너무 대충 쓰는 경우

나중에 작업 기록을 확인하기 어렵습니다.

나쁜 예시:

```txt
수정
```

좋은 예시:

```txt
월영교 장소 데이터 추가
```

## 12. 최종 요약

GitHub에서 파일을 수정하는 방식은 모든 팀원이 같습니다.

```txt
파일 클릭
↓
연필 버튼 클릭
↓
내용 수정
↓
Commit changes 작성
↓
새 branch 생성
↓
Pull Request 생성
↓
검토 후 Merge
```

역할별 수정 위치만 다릅니다.

```txt
데이터 담당자 → data/ 폴더
UI 담당자 → src/components/, src/screens/, app/ 폴더
알고리즘 담당자 → src/algorithms/ 폴더
문서 담당자 → README.md, docs/ 폴더
```

우리 프로젝트에서는 `main`에 바로 저장하지 않고, Pull Request를 통해 검토 후 반영하는 것을 기본 규칙으로 합니다.
